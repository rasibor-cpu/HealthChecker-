3. ARCHITECTURE IMPLEMENTED
────────────────────────────────────────────────────────────────
A narrowly-scoped automatic intake layer was added as a new package
(backend/health_vault/intake/) that sits in front of the existing
canonical ImportService/ImportPipeline without modifying it.

Components:
  IntakeConfig       — configuration dataclass (root path, limits,
                       allowed extensions, provenance tags, source
                       system, stale-recovery flag)
  LifecycleManager   — atomic claim (rename), terminal moves,
                       stale-processing recovery, path-traversal guard
  scan_incoming()    — non-recursive enumeration of incoming/,
                       extension / size / MIME / path-safety checks
  FileProcessor      — per-file: claim → ImportService.import_file()
                       → completed or quarantine; never raises
  IntakeRunner       — one-shot orchestrator: ensure dirs → recover
                       stale → scan → quarantine pre-rejections →
                       process each → emit privacy-safe summary

────────────────────────────────────────────────────────────────
4. CONTROLLED INTAKE DIRECTORY / STATE MODEL
────────────────────────────────────────────────────────────────
Intake root: <repo>/hc_intake/  (configurable per IntakeConfig)

  hc_intake/
    incoming/     INCOMING    — user-placed files awaiting claim
    processing/   PROCESSING  — atomically claimed (in-flight)
    completed/    COMPLETED   — successfully ingested or canonical
                               duplicate; terminal
    quarantine/   QUARANTINE  — failed, unsupported, unsafe; terminal
                               + privacy-safe .reason sidecar

Only top-level files in incoming/ are ever examined (non-recursive).
Subdirectories are silently skipped.

6. ATOMIC-CLAIM STRATEGY
────────────────────────────────────────────────────────────────
LifecycleManager.claim(incoming_path) performs:

  1. Resolve incoming_path and verify it is inside incoming_dir
     (path-traversal guard, raises → reason=path_traversal).
  2. Path.rename(processing_dir / name)
     On Windows NTFS within the same volume this rename is atomic.
     Only one caller succeeds; concurrent callers see FileNotFoundError
     and receive ClaimResult(claimed=False, reason="already_claimed").
  3. Returns ClaimResult(claimed=True, processing_path=...) on success.

No lock files, no advisory locks, no external coordination needed.

────────────────────────────────────────────────────────────────
7. IDEMPOTENCY STRATEGY
────────────────────────────────────────────────────────────────
ImportPipeline.run() performs SHA-256 content hashing and calls
ImportPipeline._find_duplicate() before any vault write.

If the same file content is re-presented:
  • Pipeline returns {"ok": True, "duplicate": True, ...}
  • FileProcessor moves the file to completed/ with status="duplicate"
  • No new document, measurement, timeline entry, or trend is created
  • Duplicate count is incremented in the run summary

This reuses the existing duplicate detection without duplicating it.

────────────────────────────────────────────────────────────────
8. RESTART / STALE-PROCESSING STRATEGY
────────────────────────────────────────────────────────────────
At the start of every IntakeRunner.run() (before scanning), when
config.stale_recovery=True (the default):

  LifecycleManager.recover_stale_processing()
    → lists processing/ directory
    → for each file found: rename to incoming/
    → logs each recovery (privacy-safe: basename only)
    → returns list of recovered basenames for summary

On the next scan pass (same run) the recovered files appear in
incoming/ and are processed normally.

If recover fails for a specific file (OSError), that file is logged
as a warning and left in processing/ (not silently dropped).
