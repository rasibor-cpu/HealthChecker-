4. ACCEPTANCE CRITERION MET (HOW)
────────────────────────────────────────────────────────────────
"After installation/activation, placing a supported medical-record
file in the configured incoming directory must cause HealthChecker
to discover and process it automatically without a user manually
invoking Python."

Mechanism:
  1. Operator runs install_intake_task.ps1.template (with approval env
     var set and elevation) — registers HealthCheckerIntake as a
     Windows Scheduled Task with 5-minute AT_LOGON repetition.
  2. Task calls: python -m backend.health_vault.intake.runner
  3. runner.main() creates IntakeRunner (which internally uses
     IntakeWatcher wrapping MonitoringScheduler for timing control).
  4. IntakeRunner scans incoming/, claims eligible files atomically,
     calls ImportService.import_file() for each, and moves each to
     completed/ or quarantine/.
  5. Every 5 minutes (by repetition trigger) the task fires again.
     MonitoringScheduler's lease prevents concurrent instances.

Not yet activated: task not registered in this session per task spec.

6. CONCURRENT-RUN EXCLUSION
────────────────────────────────────────────────────────────────
Two independent layers:

Layer 1 — Windows Task Scheduler IgnoreNew policy
  If the previous task instance is still running when the next
  5-minute trigger fires, IgnoreNew causes the new instance to be
  silently discarded.

Layer 2 — MonitoringScheduler Python lease
  Before executing the sync function, MonitoringScheduler sets
  running=True with a lease_expires_at timestamp persisted in
  VaultStore. A second watcher reading the same store sees
  running=True and returns {ran: False, reason: "already_running"}.
  Stale leases (past expiry) are cleared on reinstantiation.

Layer 3 — Atomic Path.rename() file claim (HC-312A, unchanged)
  Even if two processes reach the file-processing step, only one
  can rename incoming/<file> to processing/<file>.

────────────────────────────────────────────────────────────────
7. RESTART / REBOOT PERSISTENCE
────────────────────────────────────────────────────────────────
Windows Task Scheduler persistence:
  AtLogon trigger ensures the task resumes automatically after
  reboot when the user logs in.  No action needed by the user.

MonitoringScheduler state persistence:
  Scheduler state (last_success_at, next_due_at, consecutive_failures,
  lease) is persisted in VaultStore index.json. A fresh process
  reinstantiating IntakeWatcher with the same VaultStore reads back
  the prior state, clears stale leases, and continues from the
  correct interval.

HC-312A stale-processing recovery (unchanged):
  Files stranded in processing/ from a prior crash are moved back to
  incoming/ before the next scan.
